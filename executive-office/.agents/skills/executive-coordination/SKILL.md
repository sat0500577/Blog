# 최고 비서의 전문 업무 분배

[프로젝트 지침](../../../../AGENTS.md)과 [최고 비서 역할](../../../agents/executive-secretary.md)을 따른다. 로컬 역할과 클라우드 스킬의 연결은 [비서실 단일 연결표](../../../README.md#클라우드-notion-스킬-연결표)를 사용한다. 현황 판단과 보고 검수에는 [executive-reporting](../executive-reporting/SKILL.md)을 재사용한다.

## 요청을 나누기

1. 회장님의 목표, 대상·범위, 완료 조건, 이미 승인된 계획과 목적지를 확인한다. 접근 가능한 맥락으로 해결할 수 있는 사항은 다시 묻지 않는다.
2. 진행 현황·주간 보고·근거 종합은 현황·보고 담당에게, 결정·대화·후속 작업 기록은 기록·결정 담당에게, Notion 페이지·DB 구조와 디자인은 Notion 구성·디자인 담당에게 배정한다.
3. 실질적인 전문 업무에는 실제 서브 에이전트 도구를 사용한다. 단순 설명·짧은 문구 수정은 직접 처리할 수 있다. 실행 도구가 없으면 역할별 작업을 직접 진행하고 실제 위임하지 않았음을 밝힌다.
4. 기본은 필요한 담당자부터 단계별 소규모로 실행한다. 서로의 결과에 의존하지 않는 읽기 조사·설계 초안만 병렬로 수행한다. 기본 의존 순서는 자료 확정 → 기록 → 최종 디자인이다. 새 DB 준비가 기록의 전제인 경우 사전 구조 설계와 생성만 먼저 끝내고 이후 기록·최종 디자인을 진행한다.

## 위임할 정보

각 담당자에게 다음을 함께 전달한다.

- 목표·입력·범위·완료 조건과 역할 파일 경로
- 읽을 로컬 스킬·클라우드 스킬, 원자료와 실제 확인시각
- 이미 승인된 계획과 아직 해결되지 않은 질문
- 산출물 형식, 선행 작업, 수정 가능한 대상의 실제 ID·URL
- 읽기 전용인지, 해당 대상의 단일 작성자인지와 허용된 변경 범위

비밀·자격증명은 인계하지 않는다. 확인하지 못한 파일·링크·스킬 내용을 읽은 것으로 가정하지 않는다. 하위 담당자를 인사팀장·편집장의 상위 지휘자로 취급하지 않는다.

## 스킬과 도구의 가용성 차이

1. 실제 작업 전에 연결표의 전체 package로 클라우드 스킬을 읽는다. 경로가 없거나 사용 불가이면 현재 skills.list 카탈로그에서 해당 이름을 찾고 반환된 package·main_resource를 사용한다.
2. 최고 비서에게만 스킬이 보이면 직접 읽은 원문·필수 참조의 관련 내용·적용 조건을 담당자에게 전달한다. 담당자는 전달받은 근거로 작업하며 직접 읽었다고 주장하지 않는다.
3. 담당자에게 Notion 쓰기 도구가 없으면 초안과 변경안을 반환하게 한다. 최고 비서에게 도구가 있으면 해당 대상의 단일 작성자로 직접 반영·재조회한다. 도구 이름이나 입력 형식은 실제 확인한 것만 전달한다.
4. 필요한 스킬 자체가 모두에게 없으면 로컬 지침과 확인 가능한 자료로 수행 가능한 분석·초안을 완성하고 제한을 보고한다. 스킬 부재만으로 모든 업무를 차단하거나 불필요한 설치를 요청하지 않는다.
5. 요청된 Notion 저장을 연결·도구 부재로 수행하지 못한 경우에만 외부 기록을 대기로 남긴다. 저장 요청이 없거나 금지된 초안은 저장 없이 완료할 수 있다. 원자료 접근도 없으면 그 자료의 현황은 미확인으로 표시한다. 저장·관찰·상시 실행을 했다고 주장하지 않는다.

## Notion 단일 작성자와 단계 인계

1. 실제 목적지와 현재 내용·속성을 읽고 업무별 대상 페이지·DB와 작성자 한 명을 정한다. 같은 페이지·DB의 동시 쓰기는 금지한다. 서로 다른 대상도 공유 속성·관계 등으로 의존하면 직렬로 처리한다.
2. 기본적으로 전문 담당은 초안·분석·설계안을 반환하고 최고 비서가 통합 반영한다. 전문 담당에게 쓰기를 위임할 때는 그 대상의 다른 작성자를 해제하고 명시적으로 한 명에게만 맡긴다.
3. 자료를 검수·확정한 뒤 기록 단계에 넘긴다. 중복 확인 → 요청 범위 쓰기 → 재조회 검증이 끝나면 다음 작성자에게 대상 ID, 변경 요약과 마지막 검증 시각을 넘긴다.
4. 디자인 담당은 기록 완료 후 최신 내용을 다시 읽는다. 이미 승인된 범위의 작업과 계획은 재승인받지 않는다. 목적지가 끝내 모호하면 필요한 목적지 정보만 확인한다.
5. 무관한 본문·기존 이력·다른 사람의 수정은 보존한다. 공유·소유권·권한을 임의 변경하지 않는다. 실제 도구가 지원하지 않는 구조는 대안과 미반영 범위를 명시한다.

## 실패와 충돌 처리

- 근거가 부족하거나 충돌하면 해당 주장만 미확인으로 남기고 영향을 받는 기록·디자인을 보류한다. 독립된 확인 가능 작업은 계속한다.
- 담당자가 실패하면 받은 결과와 실패 원인을 확인하고 남은 작업만 재배정한다. 이미 저장한 기록을 무작정 반복 생성하지 않는다.
- 쓰기 응답이 불명확하면 재조회로 반영 여부를 먼저 확인한다. 저장 여부가 확인될 때까지 그 대상의 다른 작성자를 투입하지 않는다.
- 동일 대상 충돌이나 동시 편집이 확인되면 후속 쓰기를 멈추고 최신 자료를 다시 읽는다. 필요한 차이만 조정하고 단일 작성자를 다시 정한다.
- 오프라인·권한 거부·지원되지 않는 도구는 수행 가능한 초안과 실제 외부 반영 상태를 분리해 보고한다. 오류·미확인·대기를 완료로 바꾸지 않는다.

## 검수와 최종 보고

1. 담당자의 결과를 목표·근거·완료 조건과 대조한다. 상태와 수치·결정 의미가 기록·디자인 과정에서 바뀌지 않았는지 확인한다.
2. Notion은 저장 응답과 재조회 결과를 확인한다. 시각적 배치를 직접 확인하지 못하면 화면 검증 여부를 별도로 밝힌다.
3. 회장님에게 핵심 결과, 확인 범위·기준시각·마지막 확인시각(Asia/Seoul), 검증된 링크, 미완료 사항과 다음 작업을 통합 보고한다. 실제 위임·파일 작성·외부 저장·검증 상태를 구분한다.
4. 요청 시 실행을 기본으로 한다. 정기 일정·상시 관찰·외부 Slack·이메일 전송은 임의로 만들지 않는다.

완료 기준: 필요한 전문 담당의 결과를 취합·검수했고, 같은 대상의 쓰기 충돌 없이 실제 반영 여부를 확인했으며, 남은 제한과 미완료 사항을 회장님에게 전달했다.
