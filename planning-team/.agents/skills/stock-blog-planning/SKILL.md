# 주식 블로그 인터뷰와 기획서

[프로젝트 지침](../../../../AGENTS.md), [기획팀장](../../../agents/planning-lead.md), [기획서 담당](../../../agents/planning-writer.md)의 역할을 따른다. 인터뷰에는 [질문 가이드](references/interview-guide.md), 작성에는 [기획서 양식](references/planning-brief-template.md)을 읽는다.

## 원문 스킬과 기존 기능 재사용

- 질문의 의존성과 빠진 가정은 [grilling](../../../../hr-team/.agents/skills/grilling/SKILL.md)으로 점검한다. 한 번에 전체 질문을 나열하는 대신 사용자의 한 번에 1~2개 질문 선호를 우선한다.
- 콘텐츠 방향은 [content-strategy](../../../../hr-team/.agents/skills/content-strategy/SKILL.md)를 적용한다. B2B 구매 전환·고정 비율·예시 수치는 우리 사실로 사용하지 않는다. 목적은 사용자와 합의한 독자 교육·구독·신뢰 등으로 바꿔 해석한다.
- 글별 브리프는 [stock-editorial](../../../../.agents/skills/stock-editorial/SKILL.md), 자료 조사와 근거 검수는 [stock-research](../../../../.agents/skills/stock-research/SKILL.md)와 [stock-fact-check](../../../../.agents/skills/stock-fact-check/SKILL.md)를 재사용한다. 내용을 복제한 새 스킬을 만들지 않는다.
- 금융 질문 프레임이 필요할 때만 [실적 전망 참고](../../../references/financial/earnings-preview.md)와 [산업 개요 참고](../../../references/financial/sector-overview.md)를 읽는다. 이 파일은 질문 프레임용 참고자료이며 실행 스킬이나 최신 금융 데이터가 아니다.
- 경쟁 비교에는 [competitor-profiling](../../../../hr-team/.agents/skills/competitor-profiling/SKILL.md), 독자 자료 분석에는 [customer-research](../../../../hr-team/.agents/skills/customer-research/SKILL.md)를 읽는다. 회의 준비와 콘텐츠 캘린더는 [README의 Notion 플러그인 연결](../../../README.md)을 사용하고 로컬 원문 사본을 만들지 않는다. grilling의 질문 설계, content-strategy의 방향·주제축 기능은 계속 재사용한다.

## 선택 업무와 근거 기준

기존 확정 방향의 간단한 정리에는 맞춤 스킬과 필요한 기존 자료만 사용한다. 아래 네 스킬을 매번 모두 호출하지 말고 요청의 산출물과 부족한 근거에 맞는 분기만 선택한다.

- 경쟁 블로그 비교: 기획서 담당이 대상 URL·비교 깊이·범위를 받아 원문을 확인한다. SaaS 가격·기능 표를 그대로 채우지 말고 독자, 주제, 설명 방식, 원자료 인용, 글 구성과 관찰 기간의 발행 구성을 비교한다. 관찰 사실·해석·우리 기획의 선택지를 분리한다. 못 찾은 항목은 '확인한 페이지에서 미관찰'이며 부재의 증거가 아니다. SEO 도구 연결이 없으면 트래픽·검색량·순위·백링크 수치는 미확인으로 두고 정성 비교를 진행한다.
- 독자 조사: 기획서 담당이 실제 제공된 인터뷰·설문·댓글 또는 접근 가능한 공개 반응에서 출처 URL/파일·날짜·문맥·독자 집단·관찰 건수를 기록한다. 실제 인용과 요약을 구분하고 가짜 발언·독자 이력·데이터를 만들지 않는다. 자료가 없으면 미확인과 검증할 가설·수집 계획만 제시한다. 원문의 3개 출처/5개 자료 기준은 통계적 확신의 증거가 아니다. 중복·자기선택·커뮤니티 편향과 반대 사례를 살피고 전체 독자로 일반화하지 않는다. 1차 인터뷰·설문을 설계할 때 해당 원문의 필수 참고를 읽되 모집 메일·초대·보상 지급은 별도 실행 지시 없이 하지 않는다.
- 회의 준비: 팀장이 `notion-meeting-prep`로 기존 결정과 미해결 질문, 목적·안건·결정 선택지를 정리한다. 주어진 회의 시간 안에서 구성하고 모르는 날짜·참석자를 만들지 않는다. '다음 회의'의 실제 일정 선택이 필요하면 원문의 `reference/next-meeting.md`를 추가로 읽는다. 독자·경쟁 조사는 기획서 담당에게 실제 위임하고 결과를 검수한다.
- 콘텐츠 캘린더: 요청된 경우 기획서 담당이 `notion-plan-marketing-campaigns`로 주제·형식·진행 상태·승인 상태·발행 상태·담당·잠정 일자·근거를 담은 초안을 만든다. 광고 캠페인·예산·성과를 임의로 추가하지 않는다. 일정 초안은 자동화 일정이나 실제 발행이 아니다. 기존 페이지·DB·스키마를 먼저 확인하고 비서실의 기록·디자인 역할을 재사용한다.
- 모든 조사에서 비공개 원자료·개인정보·회의록 본문을 Git에 저장하지 않는다. 외부 스킬의 raw 저장 예시는 사용자 지정 비공개 위치나 저장소 밖 임시 작업 공간으로 한정하고, 출처와 공개 가능한 요약만 저장소에 남긴다. 이 스킬 도입은 외부 메시지 발송 권한이 아니다.

## Notion 연결과 인계

1. [기획 인계 절차](../../../../.agents/skills/stock-editorial/references/notion-planning-handoff.md)를 재사용해 관련 회의록을 실제 조회하고 확정·제안·미정을 나눈다. 최신 사용자 지시를 우선하며 수정시각만으로 확정 결정을 뒤집지 않는다. 조회 URL·회의일·조회일·적용 결정·미해결 사항은 공개 원고와 분리한다.
2. 플러그인 스킬의 정확한 package/resource는 README에서 확인한다. 실제 플러그인과 필요한 읽기/쓰기 도구·권한이 있어야 저장할 수 있다. 자식에게 스킬 읽기 도구가 없으면 팀장이 원문과 필요한 참고를 읽고 관련 본문·출처·도구 입력 조건을 전달한다. 자식이 직접 읽지 않은 원문을 읽었다고 보고하지 않는다.
3. 자식에게 자료 조회 도구가 없으면 팀장이 확인한 자료를 출처와 함께 전달한다. 쓰기 도구만 없으면 자식은 초안을 반환하고 팀장 또는 비서실의 지정된 한 명이 저장한다. 아무도 접근할 수 없으면 가능한 로컬 기획 초안과 접근 한계를 보고하고 필요한 링크·연결만 요청한다. 스킬만 안 보인다는 이유로 전체 업무를 중단하거나 추가 설치를 요구하지 않는다.
4. 같은 Notion 페이지·DB에는 쓰기 담당 한 명만 둔다. 검수된 자료 → 기록 → 화면 구성 순서로 ID·최신 내용·검증 결과를 넘긴다. 이미 승인된 저장은 재승인을 요구하지 않으며, 기존 내용·중복을 읽고 요청 범위만 작성한 뒤 재조회하여 링크와 남은 한계를 보고한다. 불확실한 쓰기는 성공 여부 확인 후 재시도한다.
5. 이번 구성 연결은 실제 회의록 DB 생성·Notion 저장·WordPress 발행을 수행한 것이 아니다. 저장·구성·게시 실행은 해당 요청의 범위와 도구에 따른다.

## 인터뷰 진행

1. 현재 대화와 알려진 자료에서 이미 답한 내용·확정 사항·조사할 사실을 먼저 정리한다. 에이전트가 확인 가능한 사실을 회장님에게 대신 조사해 달라고 묻지 않는다.
2. 목표와 독자처럼 뒤의 선택을 바꾸는 선결 질문부터 한 번에 1~2개만 묻는다. 답을 받은 뒤 다음 질문을 정한다. 회장님 선호·판단은 회장님에게 확인하고, 시장·플랫폼·기업 관련 사실은 접근 가능한 근거로 조사한다.
3. 질문 UI와 사용자 질문은 기획팀장만 담당한다. 기획서 담당 등 자식 에이전트는 빠진 항목과 질문 초안을 팀장에게 반환한다.
4. 핵심 목표·독자·시장·포맷·자료 근거 계획·운영 여력·성공 기준이 기획 가능한 수준이면 종료한다. 완벽한 답을 얻으려고 질문을 계속하지 않는다. 비핵심 미정은 제안과 함께 남긴다.
5. 인터뷰 결과를 확정·제안·미정으로 나눠 짧게 요약하고 확인한다. 이미 확인된 답을 재질문하지 않는다. 사용자가 가정에 기반한 초안을 요청하면 그 범위에서 가정을 명시해 진행한다.

## 기획서 제작과 검토

1. 확인된 인터뷰 결과를 기획서 담당에게 실제 서브 에이전트 도구로 위임한다. 역할·스킬 경로, 목표, 근거, 산출물, 완료 조건과 수정 범위를 전달한다. 인터뷰 중 전문 담당의 독립적인 자료 조사는 가능하지만 미정 선호를 확정한 기획서로 만들지 않는다.
2. 블로그 방향과 차별점, 적정 수의 주제축, 연재 주제, 글별 자료·반론·갱신 기준, 운영 계획·성공 기준, 편집장 인계를 작성한다. 요구가 바뀌면 영향받는 부분만 갱신한다.
3. 팀장은 회장님의 답, 사실 근거, 운영 여력, 품질 기준과 결과를 대조하고 기획 검토를 받는다. 기획팀 생성 승인과 개별 기획의 최종 승인을 구분한다. 이미 승인된 내용은 재승인을 반복 요구하지 않는다.
4. 승인된 방향은 편집장이 글별 브리프·집필·검수를 진행할 수 있는 형태로 인계한다. 결정 기록이나 Notion 저장은 [비서실](../../../../executive-office/README.md)의 기존 흐름을 재사용한다.
5. 간단한 수정은 팀장이 직접 처리할 수 있다. 서브 에이전트 도구가 없으면 역할별로 처리하고 실제 위임하지 않았음을 알린다.

## 주식 분석 범위와 실행 조건

- 사실·해석·전망을 구분하고 출처·기준일·단위·통화를 명시한다. 성공 기준은 측정 방법과 검토 시점을 합의하며 수익이나 검색 순위를 보장하지 않는다.
- 차트 요청은 이미지 해석, 가격·거래량 시계열, 지표 계산, 전략 백테스트 중 무엇이 필요한지 구분한다. 전문 스킬·원자료·실행 도구·검증 조건을 확인하기 전 분석 역량이나 데이터 연결을 완료했다고 주장하지 않는다.
- 새 라이브 데이터·금융 API·Notion 연결을 자동 설치하지 않는다. 필요한 조건은 미정·대기 사항으로 기록하고 가능한 기획 작업을 계속한다.
- 개발 요구는 콘텐츠 기획과 분리해 범위·입출력·인수 기준만 정리한다. 별도 실행 요청 없이 개발·배포·GitHub 이슈 게시·외부 발행을 하지 않는다.

완료 기준: 핵심 요구와 근거가 기획안에 반영되고 확정·제안·미정 및 승인 상태가 구분되며, 편집장이 이어받을 자료와 남은 조건이 준비되어 있다.
