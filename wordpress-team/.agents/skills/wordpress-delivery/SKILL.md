# WordPress 사이트 개선 조율

[프로젝트 지침](../../../../AGENTS.md)과 [팀 운영·스킬 연결](../../../README.md)을 따른다. 팀장은 회장님에게 직접 보고하며 전문 담당은 팀장에게 보고한다. 역할·스킬 파일은 상시 실행이나 사이트 연결을 의미하지 않는다.

## 접수와 환경 확인

1. 요청 목적·대상·기존 승인 범위를 현재 대화, 접근 가능한 코드·연결 자료에서 먼저 확인한다. 이미 답한 항목은 반복 질문하지 않는다. 부족한 핵심만 팀장이 묻고, 자식 담당자는 질문 초안을 반환한다. 사이트 URL·관리 권한·호스팅을 상상하지 않는다.
2. WordPress.com인지 자체 호스팅인지, 현재 요금제/권한에서 가능한 작업, WordPress·PHP·테마·플러그인 버전, 블록 테마/클래식 테마/페이지 빌더 여부를 확인한다. 모르면 해당 분기의 구현을 확정하지 않는다. [작업 분기와 확인표](references/delivery-checklist.md)를 사용한다.
3. 공개 URL 읽기, 코드 읽기·쓰기, 스테이징, 관리자·DB·CLI 접근, 배포를 구분한다. 도구가 있다는 이유만으로 대상 사이트 권한이나 플러그인 설치 권한을 추정하지 않는다. 자격증명을 채팅·Git에 복사하지 않으며 필요한 접근은 사용 가능한 보안 연결로 확보한다.
4. 사이트 목적·독자·구조를 바꾸는 작업은 [Notion 기획 인계 절차](../../../../.agents/skills/stock-editorial/references/notion-planning-handoff.md)의 실제 조회와 확정/제안/미정 구분을 재사용한다. 최신 사용자 지시가 우선한다. 관련 없는 작은 코드·문구 수정에 전체 조회를 강제하지 않는다. 접근 불가면 읽었다고 하지 않고 영향 범위를 표시한다.

## 외부 스킬 선택과 현 환경 적용

- 저장소 분류에는 [wp-project-triage](../../../../hr-team/.agents/skills/wp-project-triage/SKILL.md), 블록 테마에는 [wp-block-themes](../../../../hr-team/.agents/skills/wp-block-themes/SKILL.md), 플러그인 구현에는 [wp-plugin-development](../../../../hr-team/.agents/skills/wp-plugin-development/SKILL.md), 백엔드 성능에는 [wp-performance](../../../../hr-team/.agents/skills/wp-performance/SKILL.md)를 직접 읽는다. 원문이 선언한 WordPress 7.0+/PHP 7.4+와 실제 대상 버전을 대조하고 하위 버전 호환성을 추정하지 않는다. 클래식 테마·페이지 빌더에 블록 테마 절차를 강제하지 않는다.
- 원문의 `node skills/...`는 설치된 스킬 디렉터리의 절대 경로로 바꿔 실행하고 작업 디렉터리(CWD)는 실제 검사 대상 WordPress 저장소로 지정한다. 이 `/workspace/Blog`는 에이전트 정의 저장소이므로 실제 WP 프로젝트로 분류하지 않는다. 스크립트와 필요한 참고를 먼저 읽으며 원본을 즉석 수정하지 않는다. 탐지 실패 시 대상 경로와 도구 조건을 확인한다.
- wp-performance의 backend-only는 해당 원문의 범위다. 사이트 분석 담당은 별도의 브라우저·공개 HTTP 측정을 병행할 수 있다. `perf_inspect.mjs`는 WP-CLI를 통해 대상 WordPress를 부트스트랩할 수 있으므로 단순 파일 검색으로 간주하지 않는다. 정확한 `--path`/`--url`·실제 권한·운영 영향 확인 후에만 실행한다. 플러그인 설치·캐시 비우기·운영 부하 테스트는 요청 범위 밖에서 실행하지 않는다.
- 기술 SEO는 [seo-audit](../../../../hr-team/.agents/skills/seo-audit/SKILL.md)를 사용한다. 한국어 제목·설명에 영어 글자수 기준을 기계적으로 적용하지 않는다. canonical/schema 등은 테마·플러그인 소유를 확인해 중복 생성하지 않는다. 정적 fetch에서 JSON-LD가 안 보이면 부재로 확정하지 말고 실제 렌더링이나 검사 도구로 확인한다. 외부 문서의 서비스가 현재 제공되는지도 확인한다.
- UI는 [ui-ux-pro-max](../../../../hr-team/.agents/skills/ui-ux-pro-max/SKILL.md)의 `ux/style/color/typography` 등 필요한 일반 검색만 사용한다. 새 화면·전체 시각 방향에는 `--design-system`, 작은 문제에는 해당 `--domain`을 사용한다. 지원 스택에 WordPress는 없으므로 React·Tailwind를 전제하지 않고 결과를 실제 theme.json·템플릿 또는 확인한 클래식/빌더 구조로 번역한다.
- UI 검색은 실제 설치 경로의 `scripts/search.py`를 절대 경로로 호출한다. `CLAUDE_PLUGIN_ROOT`가 있다고 가정하지 않는다. Python 외 추가 의존·네트워크 연결은 이 로컬 검색의 필수 조건이 아니다. 결과는 디자인 제안이며 사용자 브랜드 확정값이 아니다. 기본은 `--persist` 없이 조회하고 미일치 결과는 한 번 좁혀 검색한 뒤 미확인으로 보고한다. 저장이 요청되면 기존 파일을 읽고 명시한 프로젝트 경로와 고유 영문 slug를 사용한다. 한국어 이름이 `default`로 정규화되어 충돌할 수 있다. `--force` 덮어쓰기는 기존 승인이 해당 변경을 포함할 때만 사용한다.

## 실제 분배와 인계

1. 실질적인 전문 업무는 실제 서브 에이전트 도구로 위임한다. 목표·역할·선택 스킬·근거·산출물·수정 가능한 파일/사이트 범위·완료 조건을 전달한다. 단순 설명·작은 수정은 팀장이 직접 처리할 수 있다. 모든 요청에 모든 담당이나 스킬을 동원하지 않는다.
2. 기본 순서는 분석·측정 → 필요한 SEO/UI 개선안 → 개발 → 기능·접근성·성능·검색 설정 검증 → 요청 범위의 배포다. 독립적인 읽기 조사만 병렬화하고 의존 작업은 앞선 근거를 받은 뒤 진행한다.
3. 분석 담당은 측정 근거·조건·문제 후보를, SEO/UI 담당은 우선순위·변경 명세·인수 기준을 개발 담당에게 넘긴다. 개발 담당이 구현 코드의 소유자가 되고 UI 담당은 설계·시각/접근성 검수를 맡는다. 같은 파일 또는 사이트 설정에는 쓰기 담당 한 명만 두고 최신 diff·ID·상태를 다음 담당에게 인계한다.
4. 자식에게 스킬/자료 도구가 없으면 팀장이 실제 원문과 필요한 참고·조회 자료·출처·도구 입력 조건을 전달한다. 자식이 직접 조회하지 않은 자료를 읽었다고 보고하지 않는다. 쓰기 도구만 없으면 변경안·패치를 반환하고 권한 있는 단일 담당이 적용·재검증한다. 아무도 접근할 수 없으면 확인 가능한 설계·체크리스트와 필요한 접근만 보고한다.
5. 실패·충돌·부분 완료는 영향 범위와 미검증 항목을 표시한다. 다른 사람의 변경을 덮어쓰지 말고 최신 상태와 충돌 부분을 읽어 병합한다. 불확실한 외부 변경은 실제 상태를 먼저 확인해 중복 적용을 피한다.

## 측정·구현·배포 기준

- 관찰·측정·추정·제안을 분리한다. 성능 결과는 대상 URL/커밋·도구 버전·시각·장치·네트워크·캐시 조건을 기록하고 전후 조건을 맞춘다. 실험실 성능과 실제 사용자 지표를 혼동하지 않는다.
- GA4·Search Console 연결이 없으면 방문자·노출·클릭·색인 상태·순위를 만들지 않는다. 공개 HTML의 검색 설정 점검과 검색 플랫폼의 실제 색인 결과를 구분한다. SEO나 속도 개선을 보장하지 않는다.
- 환경에 맞는 기존 테마·블록·빌더·SEO 플러그인을 우선 확인한다. 원본 코드·코어/외부 플러그인을 임의 직접 수정하거나 새 플러그인을 통째로 설치하는 권한을 가정하지 않는다. 필요한 최소 변경을 선택하고 저장소 규칙·지원 버전·기존 테스트를 따른다.
- 개발 요청으로 승인된 읽기·로컬 수정·적절한 테스트를 진행하고 매 단계 재승인을 요구하지 않는다. 운영 변경·삭제·마이그레이션은 정확한 대상·영향 범위·백업 상태·복구 방법과 기존 승인 범위를 확인한다. 범위 밖이거나 되돌릴 수 없는 행동만 구체적인 변경안을 준비한 후 팀장이 필요한 승인을 확인한다.
- 배포는 해당 요청에 포함된 범위에서만 한다. 팀 생성 승인을 실제 사이트 변경·발행 승인으로 보지 않는다. 검증된 결과가 있으면 승인된 배포를 불필요하게 재확인하지 않는다. 배포 후 실제 상태를 확인하고 실패 시 준비한 복구 범위로 대응한다.

## 팀 경계와 완료 보고

기획팀의 확정 방향을 재사용한다. 편집장은 개별 원고·팩트체크·이미지 제작·콘텐츠 발행 조율을 계속 맡고, 이 팀은 사이트 코드·설정·검색·화면 품질을 맡는다. UI 담당은 편집팀 이미지 제작자를 대신하지 않는다. 전사 현황·결정 기록은 비서실에 근거를 인계하며 다른 팀을 지휘하지 않는다.

최종 보고에는 요청과 완료 범위, 변경 파일/대상, 근거와 측정 조건, 검증 결과, 미검증·차단 사항, 실제 배포 상태·URL, 남은 작업을 포함한다. 접근 못한 사이트·실행 안 한 테스트·배포를 완료로 표시하지 않는다. 비공개 로그·개인정보·Notion 원문을 Git이나 공개 보고에 복제하지 않는다.

완료 기준: 필요한 담당의 산출물이 실제 근거와 연결되고, 변경이 요청 범위 안에서 검증됐거나 남은 한계가 명확하며, 사이트 접근·배포 상태를 정확히 보고했다.
